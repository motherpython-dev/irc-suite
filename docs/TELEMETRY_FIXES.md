# ТЗ исправлений: модуль «Телеметрия» (по итогам первой реальной сессии)

> **Состояние (iRC 2.36.0): Б1–Б7 сделаны.** Офлайн-проверка
> `python tools/telemetry_replay.py "<…21-10-12.ibt>"`: 141 182 кадра дошли все (отброшено 0,
> ошибок 0), 34 строки кругов, время всех кругов совпадает с `LapLastLapTime` ≤ 0.05 с
> (круг 12 = 50.668), жёлтые круги `valid: false` с причиной, высоты/сплиттер/ход амортизаторов
> в `laps_ibt.jsonl` заполнены, разбор 151 МБ — ~3.5 с. Живая проверка (п. «Живая проверка») — за пилотом.
>
> Найдено по ходу: `LapLastLapTime` сим обновляет через 1–3 с после линии, до этого там время
> **предыдущего** круга — круг теперь ждёт смены значения (до 5 с), иначе берётся время от линии
> до линии. Эталон в проверке — тоже «первое новое значение после линии», а не «через 1 с».
> Ещё одна причина лишних снимков сетапа: iRacing кладёт в `CarSetup` замеры шин
> (`LastHotPressure`, `LastTempsOMI`…) и меняет `UpdateCount` при каждом замере — они больше
> не считаются сменой сетапа.
> Плюс: снимки сетапа и сводки кругов (live и из `.ibt`) уходят на irchamps.gg
> (`POST /api/desktop/telemetry`, хранилище по машинам, на сайте не показываются).

Исходное ТЗ модуля — [TELEMETRY_SPEC.md](TELEMETRY_SPEC.md). Код —
`app/suite/modules/telemetry/__init__.py`, отвод 60 Гц — `app/suite/core/simclient.py`
(`add_tap`, `_tap_tick`).

## Входные данные для проверки (реальная сессия 2026-10-21)
- Машина `stockcars2 camaro2019` (NASCAR O'Reilly, Camaro), Talladega, онлайн-практика
  (`session_type = Practice`, `SessionNum = 2`), subsession 89538196 и 89539265.
- Папки iRC: `%LOCALAPPDATA%\iRC\telemetry\2026-10-21_*_talladega_stockcars2camaro2019_*`.
- Дамп live-каналов: `%LOCALAPPDATA%\iRC\telemetry\vars\stockcars2camaro2019_live.json` (322 канала).
- Эталон — `.ibt` iRacing за ту же езду:
  `%USERPROFILE%\OneDrive\Documents\iRacing\telemetry\stockcars2 camaro2019_talladega 2026-10-21 21-10-12.ibt`
  (151 МБ, 39 мин, 141 182 кадра 60 Гц, 274 канала). В нём `LapCompleted` идёт −1 → 32,
  `IsOnTrack` = True весь файл, `SessionNum` = 2, рабочие круги 50.7–51.3 с.

## Что получилось
В `laps.jsonl` основной сессии **одна строка**: круг 0, `samples: 2`, `t_start 5.933 → t_end 5.967`,
флаг `pit_out`. За следующие ~40 минут езды (33 круга по `.ibt`) — ни одной строки.
`status.errors = 0`. Снимки сетапа при этом продолжали писаться (9 штук до 21:09:32),
т.е. поток модуля (`_housekeeping`) жил, а кадры 60 Гц в `_on_frame` не приходили.

## Б1. Кадры 60 Гц перестают приходить, и это никак не видно (критично)

**Наблюдение.** После 2 кадров `Lap.add` больше не вызывается. По `.ibt` условия для записи
кругов выполнялись всё время (`IsOnTrack`, рост `LapCompleted`), значит кадры отсекались до
`_on_frame` или падали внутри него.

**Подозреваемые места** (проверить, какое сработало):
1. `SimClient._tap_tick`: `if ... self._snap.mode != MODE_LIVE: return`. Режим LIVE считается
   по `ReplayFrameNumEnd <= live_frame_threshold`. Если во время собственной езды в онлайн-
   практике (после рестарта/сброса сессии — в 21:04–21:09 `SessionTime` стоял на 5.967, затем
   сбросился на 4.05) этот признак давал REPLAY — отвод молчал всю сессию.
2. `_tap_tick`: `except Exception: pass` вокруг `cb(vals)` и вокруг всего `_tap_tick` в цикле
   опроса — любое исключение в `_on_frame`/`Lap.add` проглатывается без счётчика.
3. `_on_frame`: ранние `return` при `not IsOnTrack` и `self.sess is None` — без учёта.

**Что сделать.**
- Для отвода телеметрии **не использовать признак LIVE/REPLAY по ленте повтора**. Своя машина
  на трассе = данные настоящие. Отвод работает, если `IsOnTrack == True` и `IsReplayPlaying == False`
  (оба канала есть в live-дампе этой машины). Реплей-логику рейс-контроля
  не трогать.
- Убрать «немые» `except: pass` в пути кадров: считать и логировать (с ограничением частоты,
  например не чаще 1 раза в 10 с на тип ошибки, с трейсбеком первого случая).
- В `status()` добавить диагностику:
  `frames_in` (пришло в `_on_frame`), `frames_used` (дошло до `Lap.add`),
  `dropped: {not_live, not_on_track, no_session, same_tick, error}`, `last_frame_age_s`,
  `sim_mode`, `last_error`. Тогда такую поломку видно сразу.
- В UI модуля: если `IsOnTrack` и `last_frame_age_s > 3` — предупреждение «кадры не приходят».

**Приёмка Б1.** См. «Проверка офлайн» ниже — 33 круга из эталонного `.ibt`; плюс живой тест:
Test Drive 5 кругов и онлайн-практика 5 кругов после рестарта сессии → в обоих случаях
строка на каждый круг, `dropped.error == 0`.

## Б2. Имена каналов амортизаторов зависят от машины

**Наблюдение.** У `stockcars2 camaro2019` каналы называются `LFSHshockDefl`, `LFSHshockVel`
(и RF/LR/RR), плюс 360-Гц варианты `*_ST`. Модуль ищет `LFshockDefl` → везде `null`.

**Что сделать.** Строить карту каналов **из дампа** при смене машины, а не из констант:
- ход: первый существующий из `{c}shockDefl`, `{c}SHshockDefl`; скорость: `{c}shockVel`,
  `{c}SHshockVel` (c ∈ LF, RF, LR, RR); `*_ST` в live не использовать (это массивы 360 Гц).
- то же правило «список кандидатов» для высот и давлений (ниже), чтобы следующая машина не
  ломала модуль;
- в `status()` и в `vars/<car>_live.json` (поле `mapping`) показать итоговую карту
  «логический канал → имя в SDK / null».

## Б3. Высоты, сплиттер и горячие давления в live недоступны — брать из `.ibt`

**Наблюдение.** В live-дампе нет `LFrideHeight…RRrideHeight`, `CFSRrideHeight`, `LFpressure…`.
В `.ibt` они есть (`LFrideHeight`, `RFrideHeight`, `LRrideHeight`, `RRrideHeight`,
`CFSRrideHeight`, `LFpressure`…). Это ограничение iRacing (часть каналов только на диск), не баг.

**Что сделать.**
- В live-сводке оставить эти поля, но при отсутствии канала писать `null` и в строке круга
  `"missing_live": ["ride_height", "pressure"]` — чтобы было понятно, что это не ошибка.
- **Постобработка `.ibt`** (новое): после закрытия сессии (и по кнопке «Пересчитать из .ibt»
  / `POST /api/telemetry/reprocess?session=`) прочитать зарегистрированные `.ibt` через
  `irsdk.IBT` и записать `laps_ibt.jsonl` — та же схема строки, что `laps.jsonl`, но:
  высоты/сплиттер/давления заполнены, `samples` по 60 Гц, `source: "ibt"`, `ibt_file`.
  Круги резать по `LapCompleted` (как в live). Время круга — `LapLastLapTime`, взятое через
  ~1 с после смены `LapCompleted` (сим обновляет его с задержкой). Делать в фоновом потоке:
  файл 150 МБ читается десятки секунд; читать только нужные каналы (`get_all` по списку).
- `GET /api/telemetry/laps` — параметр `source=live|ibt` (по умолчанию ibt, если есть).

## Б4. Привязка `.ibt` к сессии берёт чужие файлы

**Наблюдение.** В `ibt.json` сессии 21:01 (89539265) лежит файл `… 20-52-21.ibt`, записанный
в предыдущей сессии (89538196). Причина: фильтр `mtime >= started − 120 с` + машина в имени.

**Что сделать.** Привязывать по содержимому: открыть заголовок `.ibt` (`irsdk.IBT`, session
info YAML) и сравнить `WeekendInfo.SubSessionID` (для Test Drive — 0 + время) и `CarPath`
с сессией; дополнительно — время начала файла (из имени `… YYYY-MM-DD HH-MM-SS.ibt`)
в окне [открытие сессии − 60 с, закрытие сессии]. Каждый `.ibt` — ровно в одной сессии.

## Б5. Одна сессия iRacing — несколько папок

**Наблюдение.** Subsession 89538196 записана в две папки (`…_2048_…` и `…_2101_…`), вторая
открыта через 1 с после закрытия и почти пустая; рядом сразу же открыта 89539265.
Сессия закрывается после 10 с «не connected» (загрузка/переход) и открывается заново.

**Что сделать.** При открытии искать в `index.json` сессию с тем же ключ (subsession, машина,
трасса), закрытую не более 30 минут назад, и **продолжать её** (дописывать в ту же папку,
нумерация сетапов продолжается). Новая папка — только для нового ключа.

## Б6. `session_num` и тип сессии

**Наблюдение.** `session.json`: `session_num: 0`; в круге: `session_num: 2`. При открытии папки
кадров ещё нет, `self._last` пуст.

**Что сделать.** Заполнять `session_num`/`session_type` при первом кадре и **вести список**
`sessions: [{session_num, session_type, first_seen}]` — внутри одного subsession бывает
практика → квала → гонка. Каждый круг уже несёт `session_num`.

## Б7. Мелочи
- Снимки сетапа: при неизменном sha писать нечего (так и есть), но 4 снимка за 7 с при
  `SessionTime` = 5.967 похожи на «дребезг» при загрузке сетапа — писать снимок, только если
  sha стабилен ≥ 2 с (debounce).
- `pit_stall` и `tires_stale`: live-температуры шин у этой машины есть (`LFtempCL/CM/CR`),
  а горячих давлений нет — это ожидаемо, см. Б3.

## Проверка офлайн (обязательна, без iRacing)
Сделать скрипт `tools/telemetry_replay.py <file.ibt>`: читает `.ibt` через `irsdk.IBT` и
**подаёт кадры по одному в тот же код** (`_on_frame` → `Lap` → `summary`), подменяя
`SimClient` заглушкой. Так проверяется логика кругов отдельно от отвода и сима.

Ожидания на эталонном `.ibt` (`… 21-10-12.ibt`):
1. 33–34 строки кругов (по смене `LapCompleted`), номера идут подряд.
2. Время кругов 2–7, 11–27 совпадает с `LapLastLapTime` из `.ibt` в пределах 0.05 с
   (например, круг 12 ≈ 50.668, круг 20 ≈ 50.677).
3. Медленные круги 8–10 и 29–31 (100–136 с) помечены `valid: false` с причиной
   (жёлтый / пит / off_track — какая есть в `SessionFlags`/`OnPitRoad`/`PlayerTrackSurface`).
4. Высоты/сплиттер в `laps_ibt.jsonl` не `null`; `shock_defl` не `null` (имена `*SHshock*`).
5. Время обработки 151 МБ — < 60 с, без чтения лишних каналов.

## Живая проверка
1. Test Drive, любая машина O'Reilly/Next Gen: 5 кругов → 5 строк, `status.frames_used` растёт,
   `dropped.error = 0`.
2. Онлайн-практика: выехать, вернуться в гараж, дождаться сброса/рестарта сессии, снова
   5 кругов → строки есть и после сброса; папка одна (Б5); `.ibt` только свой (Б4).
