# iRC — техническое задание

Документ, по которому ведётся дальнейшая работа. Заменяет статус «пилот
рейс-контроля»: рейс-контрол становится одним из модулей общего приложения.

Версия ТЗ: 1.1 · дата: 2026-09-01

## 0. Название и знак

Продукт называется **iRC** (полное — **iRChamps**). Всё, что делается в рамках
этого ТЗ, выходит под этим именем и с логотипом iRC:

| Где | Как |
|---|---|
| Приложение, окна, трей | `iRC` |
| Исполняемый файл, установка | `iRC.exe`, папка `iRC` |
| Данные пользователя | `%LOCALAPPDATA%\iRC\` |
| Издатель в установщике | `iRChamps` |
| Знак | `assets/logo-irc.png` — горизонтальный, в трее и на ярлыке кладётся на тёмную скруглённую плитку |
| Оверлеи трансляции | тот же знак в углу |

Логотип ichamps в продукте больше не используется. Сайты (`ichamps.ru`,
`irchamps.gg`) этим ТЗ не затрагиваются — их фавиконки и брендинг меняются
отдельно, по решению заказчика.

## 1. Что делаем

Одно приложение для организатора лиги, внутри которого модули включаются
независимо:

| Модуль | Состояние | Кому нужен |
|---|---|---|
| **A. Race Control** | работает (1.4.3) | организатор, стюард |
| **B. Broadcast Overlay** | новый | режиссёр трансляции, комментатор |
| **C. RUTP** | есть отдельный агент, нужна интеграция | все пилоты лиги |
| **D. Telemetry** | отложен | аналитика команды |

Ключевое требование: **модули не должны быть отдельными процессами**. Один
трей, один автообновлятор, один клиент irSDK на всё приложение.

### Почему один процесс — это не вкусовщина

irSDK читает shared memory сима. Три процесса, читающих её одновременно,
означают тройной опрос, три копии session YAML и три независимых
переподключения при перезапуске сима. Плюс уже пойманные грабли: клиент,
поднятый до сима, залипает на мёртвом буфере — эту логику придётся
дублировать в каждом процессе.

Один `SimClient` на приложение, модули подписываются на его снимки.

## 2. Архитектура

```
iRC.exe  (ядро: bootstrap, автообновление, откат версий)
└── бандл suite/
    ├── core/
    │   ├── simclient.py     ЕДИНСТВЕННЫЙ читатель irSDK; снимки, режимы, якорь
    │   ├── broadcast.py     broadcast-команды в сим (камеры, реплей)
    │   ├── storage.py       слой хранения (SQLite сейчас, ichamps позже)
    │   ├── server.py        локальный HTTP + SSE (общий для всех модулей)
    │   ├── tray.py          единый трей: список модулей, вкл/выкл
    │   ├── ui/              общий UI-kit оверлеев (RoundButton, RoundEntry,
    │   │                    RoundSelect, палитра ichamps, шрифты)
    │   └── modules.py       реестр модулей: start/stop, статус, конфиг
    ├── modules/
    │   ├── racecontrol/     A — то, что уже написано
    │   ├── broadcast/       B — трансляционные оверлеи
    │   ├── rutp/            C — ливреи Trading Paints
    │   └── telemetry/       D — позже
    └── web/                 панели и оверлеи (HTML, отдаются сервером)
```

### Контракт модуля

```python
class Module(Protocol):
    id: str                 # "racecontrol" | "broadcast" | "rutp" | "telemetry"
    title: str
    def start(self, ctx: Context) -> None: ...
    def stop(self) -> None: ...
    def status(self) -> dict: ...      # для трея и панели
    def routes(self) -> dict: ...      # свои HTTP-роуты, префикс /api/<id>/
```

`Context` даёт модулю: `sim` (снимки), `bus` (SSE-публикация), `storage`,
`config` (свой раздел), `logger`. Модуль не создаёт своего окна SDK и своего
сервера.

### Что переиспользуется из готового

- `irclient.py` → `core/simclient.py` (режимы LIVE/REPLAY, переподключение
  при залипшем буфере, поиск пилотов);
- `commands.py` → `core/broadcast.py`;
- `overlay.py` → распадается на `core/ui/` (виджеты, скругления, шрифты,
  палитра) и `modules/racecontrol/overlay.py` (только его панель);
- `server.py`, `storage.py`, `bootstrap/` — почти без изменений.

## 3. Модуль A. Race Control

Готов, переносится как есть. Из нового — только вынос общих виджетов в `core/ui`.

Незакрытые долги (переносим в бэклог, не блокируют переезд):

1. синтаксис админ-чат-команд не подтверждён на живой сессии;
2. детект контактов **без выезда** с трассы не реализован;
3. `audit.py` ни разу не прогонялся против маркеров iRacing.

## 4. Модуль B. Broadcast Overlay

Оверлеи для OBS. **Форма подачи — browser source, не окна Tk.** Сервер и SSE
уже есть; OBS добавляет `http://127.0.0.1:8777/ov/<name>` как источник, режиссёр
двигает и масштабирует их средствами OBS.

Управление — веб-панель `/broadcast`: что показывать, кого сравнивать, имена
комментаторов.

### B1. Башня позиций (timing tower)

Данные: `CarIdxPosition`, `CarIdxClassPosition`, `CarIdxF2Time`,
`CarIdxLapCompleted`, `CarIdxOnPitRoad`, `CarIdxTrackSurface`,
`DriverInfo.Drivers[]` (имя, номер, команда, класс).

- сортировка по позиции, мультикласс — группами;
- гэп: до лидера / до впереди идущего, переключается;
- отметки: в боксах, круг отставания, под жёлтым;
- ограничение показа: топ-N + «окно» вокруг выбранного пилота.

### B2. Стартовая решётка

Данные: `SessionInfo.Sessions[]` квалификационной сессии
(`ResultsPositions` / `QualifyResultsInfo`), fallback — `CarIdxPosition` на
прогревочном круге.

Показ парами (нечёт слева / чёт справа), имя + номер + время квалификации.

### B3. Плашка комментаторов

Ручной ввод в панели: до трёх имён, роль (комментатор / эксперт / гость),
показать/скрыть, автоскрытие через N секунд. Данных из сима не требует.

### B4. Отставание между выбранными пилотами

Панель: выбрать двух-трёх пилотов (поиск по номеру и фамилии уже написан).
Оверлей показывает дельту и её динамику (сокращается/растёт).

Считаем по `CarIdxEstTime` / `CarIdxF2Time`; для пилотов, идущих не подряд,
дельта суммируется по позициям между ними.

**Ограничение:** `F2Time` — оценка сима, на разорванном поле она грубее
секунды. Если точность не устроит, придётся считать самим по
`CarIdxLapDistPct` и темпу — это отдельная задача, решаем по факту.

### B5. Пит-стопы и резина

Счёт остановок: переход `CarIdxOnPitRoad` false→true и `CarIdxTrackSurface ==
in_pit_stall`; длительность стоянки — от входа в бокс до выезда.

**Смена резины — главный неподтверждённый пункт всего модуля.** Что известно:

- `CarIdxTireCompound` показывает компаунд по каждой машине. Это надёжно
  ловит смену *типа* (софт → хард), но в сериях с единственным компаундом
  значение не изменится, даже если резину поменяли.
- Косвенный признак — длительность стоянки: смена четырёх колёс добавляет
  секунды к заправке.

План: на первой же гонке снять `CarIdxTireCompound` и длительности стоянок,
сверить с тем, что видно в трансляции. По результату выбрать: компаунд,
порог по времени или их комбинацию. **До проверки в интерфейсе показывать
«резина: неизвестно», а не догадку** — как сейчас сделано с весом инцидента.

## 5. Модуль C. RUTP

Существующий агент (`rutp/agent`, ~830 строк, версия 1.2.1): трей, worker,
config, свой бэкенд, активация по ключу и **собственный встроенный updater**,
который подменяет файлы установки и перезапускает `RUTP.exe`.

### Решение: RUTP остаётся самостоятельным продуктом

**У RUTP есть пользователи вне лиги**, поэтому связывать его релизы с релизами
iRC нельзя. Втягивать его код в бандл тоже нельзя — пришлось бы поддерживать
две сборки одного кода с разными циклами обновления и следить, чтобы правка
для лиги не сломала внешних пользователей.

**iRC не подменяет RUTP, а управляет им как внешним приложением:**

| iRC делает | iRC НЕ делает |
|---|---|
| находит установленный агент | не встраивает его код |
| показывает статус в общем трее и панели | не обновляет его |
| запускает и останавливает | не трогает его конфиг и ключи |
| открывает настройки и папку `paint` | не дублирует работу с ливреями |
| предлагает установить, если не найден | |

Внешние пользователи продолжают ставить обычный RUTP и получать его
обновления; организатор лиги просто запускает его из общей оболочки.

Второй читатель session-данных здесь не мешает: RUTP обращается к сессии
редко — в момент её начала, чтобы получить список участников, — а не
непрерывно, как рейс-контрол.

### Что нужно доработать в самом RUTP

Обе правки маленькие и полезны в том числе внешним пользователям:

1. **Защита от второго запуска.** Сейчас её нет вовсе — ни мьютекса, ни
   занятого порта. Два запущенных агента будут одновременно писать и удалять
   файлы в папке `paint`. Проблема существует уже сегодня, но с запуском из
   iRC вероятность двойного старта резко вырастает. Лечится именованным
   мьютексом Windows: второй экземпляр показывает уведомление и выходит.
2. **Флаг `--managed`.** Запуск без собственного значка в трее (статус
   показывает iRC) и корректное завершение вместе с родителем. Аргументов
   командной строки агент сейчас не разбирает совсем.

Версия с этими правками — минимальная для полной интеграции. Если найден
агент старее, iRC работает в ограниченном режиме: показывает его статус и
кнопку «Открыть», но не управляет запуском.

## 6. Модуль D. Telemetry (позже)

Заготовка описана в скилле `iracing-irsdk` (`collector-architecture.md`):
клиент на ПК пилота агрегирует покруговые сводки (топливо, пит, резина) и
шлёт компактный JSON на сервер.

В iRC ложится естественно: тот же `SimClient`, свой раздел конфига, свой
эндпоинт выгрузки. Начинаем после того, как B и C заработают.

## 7. Общие подсистемы

**Трей.** Один значок. Меню: список модулей с галочками (вкл/выкл на лету),
«Открыть панель», «Проверить обновления», «Папка с данными», «Выход».

**Панель.** `http://127.0.0.1:8777/` — страница с вкладками по модулям.
Оверлеи трансляции — отдельные адреса `/ov/*` без интерфейса управления.

**Конфиг.** Один `config.json`, разделы по модулям:
```json
{ "modules": { "racecontrol": {"enabled": true, ...},
               "broadcast":   {"enabled": false, ...} } }
```
Модуль читает только свой раздел.

**Автообновление.** Механизм готов и проверен (бандл + sha256 + откат при двух
падениях). Переезжает без изменений; в манифест добавляется список модулей.

**Данные.** `%LOCALAPPDATA%\ichamps\suite\` — БД, конфиг, лог, версии.
Миграция из `...\racecontrol\`: при первом запуске переносим файлы, старую
папку не удаляем.

## 8. Что известно точно, а что нужно проверить

Подтверждено на живых сессиях:

- `CarIdx*` дают позиции, пит-роуд, покрытие и круги по всему полю;
- `SessionTime` в спектейте — живое время, не замирает в повторе;
- режим определяется по `ReplayFrameNumEnd`;
- `ResultsPositions` есть не всегда (в квалификации не было);
- перемотка требует **двух** вызовов `replay_search_session_time`;
- после перемотки данные поля обнуляются примерно на 10 секунд.

Не подтверждено, требует замера на гонке:

1. смена резины: меняется ли `CarIdxTireCompound` при смене на тот же компаунд;
2. точность `CarIdxF2Time` для B4;
3. состав `QualifyResultsInfo` для B2;
4. синтаксис админ-чат-команд (долг модуля A);
5. начисляются ли инциденты в хостед-сессиях (в последней гонке вес был нулевым).

## 9. Этапы

**Э1. Каркас iRC.** Ядро, реестр модулей, единый трей и панель с вкладками,
миграция данных. Race Control переезжает первым и работает как раньше.
*Готово, когда:* приложение стартует, рейс-контрол включается и выключается на
лету, автообновление работает.

**Э2. Broadcast: башня.** B1 плюс страница управления и инструкция для OBS.
*Готово, когда:* башня добавлена в OBS как browser source и корректно
показывает поле на живой гонке.

**Э3. Broadcast: остальное.** B2, B3, B4, B5 — в этом порядке; B5 после замера
резины.

**Э4. RUTP.** Сначала две правки в самом агенте (мьютекс, `--managed`),
затем модуль-управляющий в iRC: обнаружение, статус, запуск и остановка.
*Готово, когда:* RUTP запускается из общего трея, статус виден в панели,
а установленный отдельно агент продолжает работать сам по себе.

**Э5. Telemetry.** По отдельному ТЗ.

Долги модуля A (контакты без выезда, синтаксис команд, прогон `audit.py`)
закрываются между этапами, по мере появления живых сессий.

## 10. Решения заказчика

1. **Имя и репозиторий** — *решено*: `irc`, текущий репозиторий
   рейс-контроля становится его частью. Race Control переезжает первым модулем,
   отдельным клиентом больше не выпускается.
2. **RUTP и обновления** — *решено*: у RUTP есть пользователи вне лиги, поэтому
   он остаётся самостоятельным продуктом со своим циклом релизов и своим
   updater'ом. iRC им только управляет (§5).
3. **Приоритет внутри Broadcast** — открыт. Заложена башня позиций первой;
   если к ближайшей трансляции нужнее грид или плашка комментаторов, порядок
   в §9 меняется.
